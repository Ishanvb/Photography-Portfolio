# Photo manager

A passkey-protected admin panel at `/admin` for adding photos to the reel, to an
existing project, or to a brand new project — without touching code or deploying.

## Setup

### 1. Supabase

Create a free project, then:

1. **SQL editor** → run `db/schema.sql`, then `db/seed.sql`.
   The seed loads the existing site content and points at the images already in
   `public/photos/`, so nothing is re-uploaded and nothing moves.
2. **Storage** → create a bucket named `photos`, marked **public**.
   Public read only; writes require a signed token minted server-side.

### 2. Environment variables

Copy `.env.example` into Vercel (Project → Settings → Environment Variables) and
fill it in. `RP_ID` / `RP_ORIGIN` must match the domain you sign in on, or
passkeys will fail to verify.

### 3. Enrol the first passkey

Deploy, then visit **once**:

```
https://your-domain.com/admin/login?bootstrap=<ADMIN_BOOTSTRAP_TOKEN>
```

Register with Touch ID. The bootstrap token stops working the moment that first
passkey exists, so it cannot be reused even if the link leaks.

### 4. Adding her devices

She signs in at `/admin`, opens **Devices → Add another device**, and opens the
generated link on the new machine. The link is one-time and expires in 30
minutes; the passkey is created in that device's own secure hardware and never
travels. On Apple devices iCloud Keychain usually syncs the passkey to her
iPhone and iPad automatically, so this is often unnecessary.

## How the concealment works

Three layers, and they are not equally strong — worth being precise about:

| Layer | What it does | Strength |
|---|---|---|
| No link + `/admin` renders the site's own 404 | Nobody stumbles across it | Obscurity |
| Admin chunk emitted to `/admin-assets/`, which `middleware.js` 404s without a session | The management UI is never delivered to a signed-out visitor | Obscurity |
| Every `/api/admin/*` handler verifies the session server-side and answers 404 (not 401) when it fails | Nobody can read or change anything | **Real security** |

Only the third layer protects the data. The first two mean a casual visitor sees
nothing at all. Someone who reads the built JS bundle can discover that a login
page exists at `/admin/login` — that is unavoidable in a client-rendered site,
and it reveals nothing beyond the existence of a sign-in form.

`npm run smoke` asserts all of this offline.

## How content reaches the site

`/api/content` serves a JSON manifest, CDN-cached at the edge
(`s-maxage=60, stale-while-revalidate=600`), and preloaded from `index.html` so
it downloads in parallel with the JS rather than after it.

**Edits appear on the live site within about a minute.** That is the cache
window, not a bug — lower `CACHE` in `api/content.js` to shorten it.

`src/content/fallback.json` is a build-time snapshot of the current content,
generated by `npm run seed`. If the API is unreachable the site renders from it,
so a database problem can never blank the portfolio.

## Image pipeline

Originals go straight from the browser to Supabase Storage (Vercel rejects
request bodies over 4.5MB, which most full-resolution photos exceed). The server
then derives a JPEG/WebP pair with `sharp`, matching the existing hand-built
pipeline: 2400px long edge for galleries, 1200px for the reel, EXIF rotation
applied, **ICC colour profile preserved** in both encodings. The staged original
is deleted afterwards.

Upload full-resolution files — do not pre-shrink them.

## Notes

- New projects are created **unpublished**. They appear on the site only after
  Publish in the Projects tab.
- Two count labels are stored per project because the live site currently shows
  different numbers in the two places (Fashion reads "COLLECTIONS: 4" on the Work
  page and "[ Photo Collections: 16 ]" on its own page). Both are editable; the
  seed preserves exactly what is on the site today rather than silently
  "fixing" it.
- Removing the last remaining passkey is blocked, to prevent lockout.
